# 07 验收协议

这份文件回答一个问题：**怎样才算做完**。GPT 每个 WP 开工前都要读。怎么跑命令、什么时候停的操作细节在 `09-执行手册.md`。

## 1. 原则

1. **做完 = 每条 AC 都有证据**。没有证据的 AC 视为未完成。
2. **只做 WP 文件要求的事**。多做的东西会被要求删除（尤其是没要求的界面、依赖、重构）。
3. **做不到就停**，写清楚卡点；不准改测试断言、降低阈值、跳过用例、把失败写成通过、用假数据冒充真实运行结果。
4. **证据必须可复现**：给出准确的命令，总设计师会在本机重跑。
5. **停不停由 wp-check 说了算**：`node docs/blueprint/tools/wp-check.mjs WP-xx …` 的退出码 0 = 停、2 = 写清卡点后停、1 = 继续修（`09` 第 6 节）。

## 2. 证据放在哪里、长什么样

| 证据类型 | 要求 |
| --- | --- |
| 命令输出 | 一律用 `node docs/blueprint/tools/run-logged.mjs .qa/WP-xx/<名字>.log <命令…>` 运行；日志最后一行是 `[run-logged] exit=<退出码> …`。报告里写日志路径和关键数字（测试数、通过数、失败数、实测毫秒数） |
| 单元测试 | `tests/*.test.mjs`；报告里写“文件路径 + 用例名”，用例名照抄 WP 文件 |
| 浏览器场景 | `tests/browser/<场景名>.mjs`，加在 `tests/core-parity-browser.mjs` 的列表末尾；截图由 harness 存为 `.qa/<场景名>-<标签>.png`；要和效果图对照的截图用 1440×900（`09` 第 4.3 节） |
| 桌面端到端 | `tests/desktop/*.e2e.mjs`；截图存 `.qa/WP-xx/<英文名>.png`，窗口 1440×900 |
| 发布验收（只有 WP-19） | `tests/release/*.e2e.mjs`，用 `npm run test:release` 运行 |
| 文件证据 | 路径 + 大小 + SHA-256（例如备份包、安装包）；SHA-256 用 `Get-FileHash -Algorithm SHA256 -LiteralPath '<路径>'` |
| 代码改动 | 报告第 4 节逐个列出 `git diff --name-only main...HEAD` 里的每一个文件，每个一句话说明为什么改 |
| 人工检查项 | 只有确实无法自动化时才允许，写清楚步骤和观察到的结果，并配截图 |

`.qa/` 不进 Git（在 `.gitignore` 里），总设计师直接在本机查看。

## 3. 全局完成定义（每个 WP 都必须满足，记为 G1–G9）

| 编号 | 要求 | wp-check 里对应的检查 |
| --- | --- | --- |
| G1 | `npm test` 全部通过，0 失败，报告写明“N 个文件 / M 个用例” | K7 |
| G2 | `npm run build` 成功；WP-03 起，桌面 WP 的测试版和正式版打包都成功 | K8、K10 |
| G3 | 改动了界面的 WP：全部浏览器场景仍然通过，且每个基线场景的检查数不少于 WP-00 记录的数；WP-03 起桌面端到端测试全部通过 | K9、K10 |
| G4 | 端到端测试中没有被拦截之外的网络请求，没有 `pageerror`，没有控制台 error（`tests/desktop/helpers.mjs` 的 `assertNoNetworkAndErrors`） | K10（随测试执行） |
| G5 | 没有修改范围外的文件；报告第 4 节说明了每个改动的文件 | K4、K11 |
| G6 | 没有新增未批准的依赖；版本精确；WP-03 起 `dependencies` 只放主进程运行时要用的包；`package-lock.json` 的变化与依赖变化一致 | K5 |
| G7 | 所有提交在 WP 文件写的分支上，提交说明以 `WP-xx: ` 开头，结束时 `git status` 干净 | K1、K2、K3 |
| G8 | 没有读写用户真实数据（浏览器配置、真实数据目录、`%APPDATA%\Life Atlas`、凭证文件）；没有在 4173、4175 端口启动服务；测试全部使用临时目录或全新的浏览器上下文 | 总设计师人工检查 |
| G9 | 报告完整：第 0 节每个步骤“完成”，没有“【待填写】”，每条 AC 写明“通过 / 未通过 / 未验证”和存在的证据路径；有未通过的 AC 时第 7 节写清原因 | K11、K12 |

WP-20 起还有 K13：收尾时旧 CSS 里不能有待换算成主题变量的颜色（`src/ui/themes/`、`src/vault-ui/`、`src/setup-ui/` 不检查）。

## 4. 报告

- 报告文件 `docs/blueprint/reports/WP-xx-report.md` 由 `node docs/blueprint/tools/wp-check.mjs WP-xx --init-report` 生成骨架，有固定的 9 节：0 步骤进度、1 我的理解、2 完成情况总览、3 关键命令与结果、4 改动清单、5 自行决定的事项、6 发现的问题与建议、7 未完成/未验证、8 返工记录。
- 不要删除任何小节或表格行；不要把 wp-check 的结果表抄进报告（它自己写到 `.qa/WP-xx/wp-check.md`）。
- 第 5 节还要写：视觉闸门用户选了什么（用户原话；现在只有 WP-19 的图标）、规格没写到时按 `12` 选的最接近效果图的做法、按 `09` 第 4.5 节改过的已有测试（哪个文件、哪一行、为什么）。

## 5. 已有测试什么时候可以改

只有 `09` 第 4.5 节列出的三种情况可以改，而且断言的内容不能变。WP 文件里写明“按规定修改”的测试，照 WP 文件写的改，一个字都不多改。

## 6. 返工规则

- 总设计师验收后给出编号的问题清单（R1、R2……）。
- 返工只改清单里的问题，不顺便做别的。
- 每个问题在报告第 8 节写：原因、改动、新证据。
- 返工完成后重新运行 WP 文件“收尾”步骤里的 wp-check 命令，退出码 0 或 2 时停止。
- 同一个问题返工两次仍未解决，停下来说明原因，由总设计师调整方案。

## 7. 总设计师的验收清单（GPT 不需要执行，供审查用）

1. 在本机重跑 `node docs/blueprint/tools/wp-check.mjs WP-xx`（带 WP 文件收尾步骤里的选项），结果与 GPT 的回复一致。
2. 报告第 1 节的理解与 WP 目标一致；理解题回答正确；没有偷换需求。
3. 抽查 2–3 条关键 AC：打开对应的测试文件看断言是否真的检查了 AC 说的东西，重跑对应命令。
4. `git diff main...HEAD`：有没有范围外改动、隐藏的降级（注释掉的测试、放宽的断言、写死的测试专用分支、`if (process.env.LIFE_ATLAS_TEST)` 之外的测试后门）。
5. 数据安全：迁移是纯函数且幂等；覆盖前有快照；没有碰真实数据；删除都进回收站。
6. 密钥相关：明文扫描结果；密钥库通道只认密钥库窗口；日志里没有内容或密钥。
7. 界面：按第 8 节把截图和效果图并排对照；符合 `12-视觉规范-墨白.md` 和 `AGENTS.md` 规则；没有假入口、占位文案、右侧详情栏。
8. 下一个 WP：它写到的文件、函数、行号、测试名在当前代码里都还存在；不存在就先修订下一个 WP 文件。
9. 结论：通过（并提醒用户发合并提示词）或编号的返工清单。

## 8. 视觉对照（改动了界面的 WP；总设计师执行）

1. **参照图**：新界面用 `docs/blueprint/design/mobai/shots/` 里对应的画面（`12` 第 7 节写了每个界面对应哪个画面）；WP-20 用 `docs/blueprint/design/mobai/product-shots/`。**实际截图**是 GPT 按 WP 文件截的 1440×900 截图，白天和夜间各一张（浏览器场景在 `.qa/<场景名>-<标签>.png`，桌面在 `.qa/WP-xx/`）。
2. **生成对照图**：参照图目录里要比较的每张图都必须有实际截图（缺一张就退出码 1）。实际截图名是 `<前缀><参照图名>` 时（例如参照图 `vault-setup-light.png`，实际截图 `.qa/WP-07/shots/vault-setup-light.png`），用 `--only` 只比这个 WP 涉及的画面：

   ```powershell
   node docs/blueprint/tools/compare-shots.mjs docs/blueprint/design/mobai/shots .qa --prefix <场景名>- --only <画面>,<画面> --out .qa/WP-xx/compare
   ```

   桌面截图把第二个参数换成 WP 文件规定的截图目录（例如 `.qa/WP-07/shots`），不加 `--prefix`。名字对不上时，先把参照图复制到 `.qa/WP-xx/ref/`、改成实际截图去掉前缀以后的名字，再用 `.qa/WP-xx/ref` 当参照图目录。WP-20 直接运行 `node docs/blueprint/tools/compare-shots.mjs docs/blueprint/design/mobai/product-shots .qa --prefix wp20-mobai- --out .qa/WP-20/compare`。
3. **逐张看**：打开 `.qa/WP-xx/compare/` 里的并排图（左参照、右实际、下面红色差异图），按 `12` 第 11 节检查布局、字体（全部是无衬线字体，标题粗体）、颜色（只有灰阶和 Notion 蓝，用户内容的颜色和“今天”的红色除外）、线条（表格是浅灰网格线）、间距，再问一句“Notion 里这个地方是这样吗”；再确认浏览器场景里 `getComputedStyle` 的颜色和字体检查都通过。`summary.md` 的差异占比只供参考：只差日期、时间这类文字时也可能很大，结构不同时也可能很小，以看到的为准。
4. **结论**：不一致的地方写进返工清单（第 6 节的 R1、R2……），每条写画面名、位置、和参照图哪里不同、对应 `12` 的哪一条。参照图本身有问题时（例如效果图没画到的状态），由总设计师修订 `12` 或 `design/mobai/`，不算 GPT 的返工。
