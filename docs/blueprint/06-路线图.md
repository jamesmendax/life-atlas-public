- **视觉闸门**：现在只剩 WP-19 的应用图标：GPT 在那个步骤停下，用户从总设计师准备的 3 个图标方向里选一个（可以先让总设计师评审），再继续。界面风格已经定为墨白（`01` 的 D-25，`12-视觉规范-墨白.md`）：写着“已定：墨白（12）”的 WP 不再出方向，直接按 12 和 `design/mobai/` 的效果图做。WP-07 的步骤 1、WP-09 的步骤 1、WP-10 的步骤 6 原来是闸门，现在是普通停止点（对照效果图与理解确认），用户用 `08` 第 3 节继续。

## 2. 依赖关系

```
WP-00 → WP-01 → WP-02 → WP-03 → WP-20 → WP-04 → WP-05 → WP-06 → WP-07 → WP-08
                                                 │
WP-01 ───────────────────────────────────────────┴─→ WP-09 → WP-10
WP-07 → WP-11
WP-05 → WP-12 → WP-13
WP-04 → WP-14、WP-15、WP-16、WP-17、WP-18
WP-20 → WP-04 之后每个有界面的 WP（按 12 和 design/mobai/ 的效果图做）
全部 → WP-19
```

- Schema 版本按编号依次增加：v11（WP-01）→ v12（WP-04）→ v13（WP-10）→ v14（WP-12）→ v15（WP-13）→ v16（WP-16）。每个迁移都链在前一个后面，所以这几个 WP 的先后不能对调。WP-20 不升 schema 版本（`ui.preferences.theme` 在读取时补默认值，`02` 第 12 节）。
- 并行只在用户明确要求、并经总设计师确认没有冲突时进行；每条线一个独立分支，由总设计师审查后依次合并。

## 4. 每个 WP 的标准节奏

1. 用户把 `08-交给GPT的提示词.md` 第 2 节的提示词发给 GPT（第一次接手时用第 1 节）。
2. GPT 做到第一个停止点，用固定格式回复。用户按回复里“需要用户做的事”处理：
   - 普通停止点：发 `08` 第 3 节“继续 WP-xx”；想先让总设计师看一眼，就在 Claude 里说“看一下 WP-xx 的进度”；
   - 对照效果图的停止点（WP-07 步骤 1、WP-09 步骤 1、WP-10 步骤 6、WP-20 步骤 6）：和普通停止点一样发 `08` 第 3 节；WP-20 步骤 6 建议先在 Claude 里说“看一下 WP-20 的对照图”，总设计师看过视觉对照图再继续；
   - 视觉闸门（只有 WP-19 的应用图标）：看总设计师准备的对照图（可以请总设计师评审），然后发 `08` 第 4 节，写明选了哪个方向；
   - 卡住：把回复转给总设计师，说“WP-xx 卡住了”。
3. 重复第 2 步，直到 GPT 回复“已完成”。
4. 用户在 Claude 里说“验收 WP-xx”。总设计师重跑 wp-check、读报告、看改动和截图（有界面改动时按 `07` 第 8 节和效果图并排对照），给出“通过”或编号的返工清单（返工用 `08` 第 5 节）。
5. 通过后，用户发 `08` 第 9 节的合并提示词，GPT 把分支合并到 `main`。
6. 总设计师在验收时会顺便核对下一个 WP 文件里写的文件名、函数和行号是否还对得上；对不上会先修订 WP 文件，再开始下一个。
