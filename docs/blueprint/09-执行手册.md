# 09 执行手册（GPT 每次开工都要读）

这份手册规定**怎么做**：用什么命令、按什么顺序、遇到问题怎么处理、什么时候停。WP 文件规定**做什么**。两者冲突时以 WP 文件为准；WP 文件没写到的操作细节，以本手册为准。

## 1. 你所在的环境

| 项目 | 事实 |
| --- | --- |
| 系统 | Windows 11 |
| 你的 shell | **Windows PowerShell 5.1**（不是 bash，也不是 PowerShell 7） |
| 项目根目录 | `C:\Projects\life-atlas`（所有命令都在这里运行） |
| Node / npm / git | Node 24.17、npm 11.13、git 2.54，都已在 PATH 里 |
| 浏览器测试 | Playwright 1.63 + 本机 Edge（`channel: "msedge"`），已安装 |
| Electron | 44.4.5，本机缓存里已有安装包（WP-03 安装） |

每次开工第一条命令：

```powershell
Set-Location -LiteralPath 'C:\Projects\life-atlas'
```

## 2. PowerShell 规则（照做，不要换写法）

1. **一行只写一条命令**。不要用 `&&`、`||`（PowerShell 5.1 不支持）。需要多条命令时分多行依次运行。
2. 每条重要命令后检查退出码：`$LASTEXITCODE`（`0` 表示成功）。
3. **需要留证据的命令一律用 run-logged 运行**，不要用 `>`、`Tee-Object`、`Out-File`（5.1 会把日志写成 UTF-16，无法检查）：
   ```powershell
   node docs/blueprint/tools/run-logged.mjs .qa/WP-01/step3-npm-test.log npm test
   ```
   日志最后一行是 `[run-logged] exit=<退出码> ...`。
4. 路径里有 `[`、`]`、`*`、`?` 时，用 `-LiteralPath`。
5. 设置环境变量：`$env:NAME = "value"`；用完删除：`Remove-Item Env:NAME`。不要用 `set NAME=value` 或 `export NAME=value`。
6. 不要用 `grep`、`wc`、`ls -la`、`cat`、`rm -rf`、`sed`。搜索代码用 `git grep -n "关键词"`；看文件用你的文件读取工具。
7. 创建或修改文件用你的文件编辑工具，不要用 `echo ... > 文件`。
8. 终端里中文显示乱码不代表文件坏了；以编辑工具打开看到的内容为准。
9. 命令里需要引号时，外层用单引号 `'...'`（PowerShell 不会展开里面的 `$`）。

## 3. Git 例行操作

### 3.1 开工（每个 WP 的步骤 0）

```powershell
git status --porcelain
```

必须没有任何输出。有输出就**停下**，在回复里列出这些文件，等用户处理（不要提交、不要丢弃）。

```powershell
git switch main
git switch -c <WP 文件头部写的分支名>
```

WP 文件说“跑基线 `npm test`”时，一律用这条命令，日志名固定（第 7 节“不确定是不是你引起的”要拿它对照）：

```powershell
node docs/blueprint/tools/run-logged.mjs .qa/WP-xx/step0-npm-test.log npm test
```

说“跑基线 `npm run test:parity:browser`”时，日志是 `.qa/WP-xx/step0-browser.log`。

### 3.2 每一步结束

```powershell
git add -A
git commit -m "WP-xx: <英文简述，说明这一步做了什么>"
```

- 提交说明**只用英文、数字和常见符号**，必须以 `WP-xx: ` 开头（例：`WP-01: add schema v11 trash group fields`）。
- 提交前确认没有把不该提交的文件加进去：`git status --porcelain` 里不应出现 `.qa/`、`dist/`、`release/`、`.devdata/`、`node_modules/`（它们在 `.gitignore` 里）。

### 3.3 禁止的 Git 操作

`git push`、`git reset --hard`、`git clean`、`git checkout -- <文件>`、`git restore`（丢弃改动）、`git rebase`、`git commit --amend`、`git stash`、`git merge`、`git branch -D`、修改 `main` 分支、修改全局 git 配置。

唯一的例外：用户发来 `08-交给GPT的提示词.md` 第 9 节的合并提示词时，只按那段提示词把已经验收通过的分支合并到 `main`，然后停止。

### 3.4 中断后继续

```powershell
git status --porcelain
git log --oneline main..HEAD
```

对照报告第 0 节的步骤进度，从第一个不是“完成”的步骤继续。工作区里有未提交的改动时：如果能看懂、属于当前步骤，继续完成后提交；看不懂就停下报告，不要丢弃。

## 4. 测试怎么跑、怎么写

### 4.1 命令

| 层级 | 命令 | 说明 |
| --- | --- | --- |
| 单元测试 | `npm test` | 运行全部 `tests/*.test.mjs`（WP-00 建立） |
| 浏览器场景 | `npm run test:parity:browser` | 自动在 127.0.0.1:5178 启动它自己的 Vite，并只结束它自己启动的服务；场景列表在 `tests/core-parity-browser.mjs` |
| 只跑指定浏览器场景 | `$env:PARITY_ONLY = "wp01-integrity"` 然后 `npm run test:parity:browser`，最后 `Remove-Item Env:PARITY_ONLY` | WP-00 加入此功能；多个场景用逗号分隔 |
| 桌面端到端 | `npm run test:e2e:desktop` | WP-03 起；运行前先 `npm run build`，用到打包版的用例还要先 `npm run desktop:build:test` |
| 构建 | `npm run build` | |
| 打包 | `npm run desktop:build`、`npm run desktop:build:test` | WP-03 起 |
| 发布验收 | `npm run test:release` | 只在 WP-19 运行（WP-19 建立；会静默安装“安装测试版”，很慢） |

### 4.2 单元测试写法

- 文件放在 `tests/` 下，文件名以 `.test.mjs` 结尾，`npm test` 会自动包含。
- 开头固定写法（和现有测试一致）：
  ```js
  import test from "node:test";
  import assert from "node:assert/strict";
  ```
- 用例名**照抄 WP 文件里给出的英文名字**，一个字都不要改（总设计师按名字查找证据）。
- 被测的纯函数一律通过参数拿时间（`now`）和 ID 生成器（`idFactory`）；测试里不要依赖真实时间。
- 单元测试不访问网络、不写项目目录。需要写文件时用：
  ```js
  import fs from "node:fs";
  import os from "node:os";
  import path from "node:path";
  const dir = fs.mkdtempSync(path.join(os.tmpdir(), "life-atlas-test-"));
  // …测试结束时：
  fs.rmSync(dir, { recursive: true, force: true });
  ```
- 夹具用 `tests/fixtures/full-workspace.mjs`（`10-测试夹具规格.md`），不要自己另造一份相似的数据。
- **迁移测试要经得起以后的版本升级**：测试某一版迁移（例如 v11）时，调用那一版的迁移函数（`migrateTrashGroups`），断言写死那一版的版本号（11）；**不要**用 `upgradeWorkspace`，因为以后的 WP 会让它产生更高的版本和更多的变化。只有“升级到当前版本”的测试才用 `upgradeWorkspace`，并且与 `CURRENT_SCHEMA_VERSION` 比较，不写死数字。

### 4.3 浏览器场景写法

- 参考现有的 `tests/browser/phase3-workspace.mjs` 的结构：
  ```js
  import { browserScenario } from "./harness.mjs";
  import { fullWorkspace } from "../fixtures/full-workspace.mjs";

  await browserScenario("wp01-integrity", async ({ page, check, screenshot, saved, persisted, assert }) => {
    await check("Folder moves to trash as one group", async () => {
      // 用 page 操作界面，用 assert 断言
    });
    await screenshot("trash-folder-group");
  }, { workspace: fullWorkspace() });
  ```
- 场景名用 `wpXX-简称`，文件名与场景名相同（`tests/browser/wp01-integrity.mjs`）。
- **新场景必须加到 `tests/core-parity-browser.mjs` 里 `scenarios` 数组的末尾**，否则不会被运行。
- 每个 `check("英文标题", …)` 是一个检查项；标题照抄 WP 文件给出的名字。
- 截图由 harness 保存为 `.qa/<场景名>-<标签>.png`（例 `.qa/wp01-integrity-trash-folder-group.png`）。报告里就引用这个路径。
- 要和效果图对照的截图（`12-视觉规范-墨白.md` 第 11 节）用 1440×900：在 `browserScenario` 的第三个参数里加 `viewport: { width: 1440, height: 900 }`（harness 默认是 1440×1040）。
- 这类截图白天、夜间各一张，文件名在画面名后面加 `-light`、`-dark`，有参照图的画面名和参照图相同（例如 `timeline-light`）：浏览器场景存为 `.qa/<场景名>-<画面>-<light|dark>.png`（WP-12 起用 harness 的 `shootBothModes`）；桌面端到端存为 `.qa/WP-xx/shots/<画面>-<light|dark>.png`（WP-05 起用 helpers 的 `shootWindowBothModes`）。
- 场景里不要用固定的 `page.waitForTimeout` 等待超过 1000 ms；等待界面变化用 `page.waitForSelector`、`locator.waitFor` 或 harness 的 `persisted(...)`。
- 选择元素优先用 `getByRole`、`getByLabel`、`getByText`；需要时可以给界面元素加 `data-testid`（只加在本 WP 改动的元素上）。

### 4.4 桌面端到端写法（WP-03 起）

- 文件放 `tests/desktop/`，文件名以 `.e2e.mjs` 结尾。
- 统一用 `tests/desktop/helpers.mjs`（WP-03 建立）的 `launchApp({ packaged, dataRoot, env })` 与 `closeApp(app)`；每个用例一个新的临时数据目录。
- 每个用例结束前都要调用 helpers 里的 `assertNoNetworkAndErrors(app)`（WP-03 建立）。
- 截图存 `.qa/WP-xx/<英文名>.png`，窗口尺寸 1440×900。

### 4.5 什么时候允许改已有测试

- **不允许**：删除用例、删除或放宽断言、加 `skip`/`only`/`todo`、调大超时来掩盖问题、修改阈值。
- **允许**（并且必须在报告第 4 节逐条写明“哪个文件、哪一行、为什么”）：
  1. 本 WP 按规格改变了界面的**操作方式**（例如原生下拉框换成自绘选择器、`window.confirm` 换成产品对话框），可以修改测试里“怎么操作”的代码，断言的内容不变；
  2. WP 文件明确写了要改的测试；
  3. 修复测试之间的相互干扰（例如全局状态没有清理），不改变断言。

## 5. 报告与进度

1. 步骤 0 运行 `node docs/blueprint/tools/wp-check.mjs WP-xx --init-report` 生成报告骨架 `docs/blueprint/reports/WP-xx-report.md`。
2. 第 1 节“我的理解”在步骤 0 写完，包括回答 WP 文件步骤 0 里的理解题。
3. **每完成一个步骤**：把报告第 0 节对应行的状态改成“完成”，和这一步的代码一起提交。
4. 证据：
   - 命令日志：用 run-logged 写到 `.qa/WP-xx/`；
   - 浏览器场景截图：`.qa/<场景名>-<标签>.png`；
   - 桌面截图：`.qa/WP-xx/`；
   - 自动化测试：写“测试文件路径 + 用例名”。
5. 第 2 节每条 AC 的结论只能写“通过 / 未通过 / 未验证”。没有实际运行过的写“未验证”。
6. 第 4 节列出 `git diff --name-only main...HEAD` 里的**每一个**文件，每个一行，说明为什么改（wp-check 会逐个核对）。
7. 不要在报告里写 wp-check 的结果表——它自己会写到 `.qa/WP-xx/wp-check.md`。

## 6. 什么时候停（唯一标准）

### 6.1 三种停止

| 情况 | 你要做的 | 然后 |
| --- | --- | --- |
| 走到标着 **【停止点】** 的步骤 | 完成该步骤，提交，运行该步骤写的 wp-check 命令（通常是 `--until <步骤号>`），直到退出码为 0 | **停止**，按 6.2 回复 |
| 全部步骤完成 | 运行 WP 文件“收尾”步骤里写的 wp-check 命令 | 退出码 0 或 2：**停止**，按 6.2 回复；退出码 1：继续修 |
| 卡住（第 7 节的表格让你停） | 在报告第 7 节写清：卡在哪一步、做了什么尝试、错误信息、证据路径；提交 | **停止**，按 6.2 回复 |
| 任何时候 wp-check 的 K0 失败（WP 文件“必读”里的文件不存在） | 先用 `git grep -n "<文件名>"` 找一次；仍找不到，在报告第 7 节写“锚点不存在：<文件>”，提交 | **停止**，按 6.2 回复（状态写“卡住”）；不要自己创建这些文件 |

wp-check 退出码：

- `0`：全部通过 → 停止。
- `2`：两种情况，都要**停止**：① 机械检查都通过，但报告里有 AC 是“未通过/未验证” → 确认报告第 7 节逐条写明原因；② K0 失败（规格和代码对不上）→ 按上表最后一行处理。
- `1`：还有检查没通过 → 按输出逐条修复、提交、重新运行。**同一项检查连续修 3 次仍然失败**，就把情况写进报告第 7 节，提交，然后停止。

### 6.2 停止时的回复（固定格式，不要加别的）

```
WP-xx 状态：已完成 / 已到停止点（步骤 N） / 卡住（步骤 N）
wp-check 退出码：0 / 2 / 1
报告：docs/blueprint/reports/WP-xx-report.md
需要用户做的事：……（没有就写“无”）
```

### 6.3 停止后

不要再修改任何文件，不要开始下一个步骤或下一个 WP，不要“顺手优化”。等用户的下一条指令。

## 7. 卡住时怎么办（照表处理，不要自由发挥）

| 情况 | 做法 | 不要做 |
| --- | --- | --- |
| 开工时 `git status --porcelain` 有输出 | 停下，列出文件，等用户处理 | 提交、丢弃或忽略它们 |
| WP 里写的文件、函数、搜索词在代码里找不到 | 用 `git grep -n "<词>"` 再找一次；仍找不到就停下，在报告第 7 节写“锚点不存在：……” | 自己猜一个相近的位置去改 |
| 步骤 0 的基线 `npm test`（还没改任何代码）就有失败 | 停下报告失败的用例名和日志路径 | 修它、跳过它 |
| 改到一半发现一个失败，不确定是不是你引起的 | 对照步骤 0 的基线日志 `.qa/WP-xx/step0-npm-test.log`：基线里通过、现在失败，就是你引起的，必须修好 | 认定“和我无关”而不处理 |
| 你的改动让现有测试失败 | 修你的代码，直到通过 | 改断言、加 skip、删用例 |
| `npm install` 失败（网络、证书、超时） | 等 1 分钟重试 1 次；仍失败就停下，报告完整错误 | 换镜像源、换包、加 `--force` 或 `--legacy-peer-deps` |
| 浏览器场景报 `browser close exceeded` | 再运行一次；连续两次都这样就停下报告 | 改 harness 的超时（WP-00 已经调整过） |
| 端口 5178 被占用 | `Get-NetTCPConnection -LocalPort 5178` 查看；如果是你自己之前启动的 node 进程，结束它；否则停下报告 | 结束不是你启动的进程；换用 4173/4175 端口 |
| 规格里两处说法矛盾 | 以 WP 文件为准；WP 文件内部矛盾就停下报告 | 自己挑一个 |
| 规格没写到的小细节（文案、样式、变量名、文件内部结构） | 选最简单、和周围代码一致的做法，写进报告第 5 节 | 停工等待 |
| 规格没写到，而且涉及数据格式、加密、删除或覆盖用户数据、新依赖、新接口 | 停下，在报告第 7 节提问 | 自己决定 |
| 想顺手修别的问题 | 写进报告第 6 节 | 动手修 |
| 一个测试时好时坏 | 用 run-logged 连续跑 5 次记录结果，找原因（计时器、全局状态、等待条件）并修复；修不好就停下报告 | 加重试、加大超时来掩盖 |
| 命令超过 10 分钟没有任何输出 | 结束它，在报告记录，再运行一次；还卡住就停下报告 | 反复重启 |
| 不确定某个界面该长什么样 | 看 WP 文件里的描述、`12-视觉规范-墨白.md` 和 `docs/blueprint/design/mobai/shots/` 里对应的画面（可操作的原型是 `docs/blueprint/design/mobai/prototype/index.html`，只看不改）；还不确定就选和效果图最接近的做法，写进报告第 5 节 | 发明新的视觉风格；修改 `src/ui/themes/mobai/` 里从蓝图复制来的 8 个样式文件 |
| 发现 `docs/blueprint/` 的设计有错 | 写进报告第 6 节，按原设计继续；原设计确实无法实现时停下 | 修改设计文档 |

## 8. 全局禁止清单

1. 读取或修改：用户真实的浏览器与浏览器配置、`%APPDATA%`/`%LOCALAPPDATA%` 下的任何用户数据、`.visual-qa/`、任何密码/密钥/凭证文件、`D:\LifeAtlas`（用户将来的真实数据目录）。
2. 在 4173、4175 端口启动任何服务（那是用户真实数据所在的浏览器地址）；用用户自己的浏览器打开预览。需要看界面时只用 Playwright 新开的浏览器。
3. 运行 `npm run verify:parity:delivery`、`npm audit fix`、`npm update`、`npx <任何需要下载的工具>`。
4. 修改 `docs/blueprint/` 下除 `reports/WP-xx-report.md` 以外的任何文件；修改 `AGENTS.md`；修改 `docs/blueprint/tools/` 下的工具。
5. 修改 `node_modules/`，给依赖打补丁。
6. 产品代码里出现网络请求（访问 http/https/ws 的 fetch、XMLHttpRequest、WebSocket）、遥测、CDN、在线字体、自动更新。
7. 新增 `docs/blueprint/02-总体架构.md` 第 11 节以外的依赖。
8. 在测试里使用真实的 Windows 用户目录作为数据目录或 bootstrap 目录。
9. 删除不是你在本 WP 里创建的文件（WP 文件明确要求删除的除外）。
