# 03 密钥库安全设计

这是全项目最不能出错的部分。本文件里的算法、参数、格式、字符串常量都是**规定**，不是建议。执行者不得替换算法、调低参数或改变格式；觉得有问题就在报告里提出，由总设计师修订。

## 1. 目标

1. 用户在一个独立、私密的地方保存各种账号、密码、API Key、服务器凭据、恢复码等。
2. 进入必须输入主密码；离开、闲置、锁屏后自动上锁。
3. 磁盘上（数据库、日志、快照、缓存、备份包）**任何地方都没有明文**。
4. 工作区里的页面即使渲染了恶意内容，也拿不到密钥。
5. 备份导出时密钥库保持加密；导入后用原主密码或恢复密钥解锁，内容完全一致。

## 2. 威胁模型（界面“安全说明”里要用通俗语言向用户说明这一节）

| 场景 | 能否防住 | 依靠什么 |
| --- | --- | --- |
| 数据目录或备份文件被复制走（电脑丢失、被拷贝、同步盘泄露） | ✅ 能 | AES-256-GCM 加密 + Argon2id（128 MiB 内存）拖慢暴力破解。前提：主密码足够强 |
| 别人趁你离开时打开你的电脑和 Life Atlas | ✅ 能（密钥库已上锁时） | 闲置自动上锁、系统锁屏/睡眠即上锁、进入需要主密码、敏感操作再次验证 |
| 导入的网页/Markdown/HTML 内容里藏有恶意脚本 | ✅ 能 | 密钥库在独立窗口和独立进程；工作区窗口没有任何密钥通道，也从不出现主密码输入框；严格 CSP |
| 截图、录屏、远程桌面截屏软件 | ✅ 大部分能 | 密钥库窗口开启 `setContentProtection(true)`（Windows 下截到的是黑色） |
| 复制密码后忘记清剪贴板 | ✅ 能 | 到时自动清除（仅当剪贴板内容仍是那条密码）。注意：Windows“剪贴板历史”（Win+V）可能另存一份，见 WP-11 |
| 有人篡改数据库里的密文 | ✅ 能发现 | AEAD 认证 + 附加数据绑定，篡改或互换条目都会解密失败并提示 |
| 旧主密码或旧恢复密钥泄露了，你已经修改 | ✅ 能保护修改之后的内容 | 每次修改主密码或重新生成恢复密钥都会更换数据密钥并重新加密全部条目（第 4 节）。修改之前留下的快照和备份仍然只能用当时的密码打开当时的内容 |
| 反复猜密码 | 🟡 部分 | 应用内失败 5 次后递增等待；但拿走文件离线猜的人不受此限制，只能靠 Argon2id 和密码强度 |
| 电脑已中木马（键盘记录、读内存），且你在中招期间解锁过 | ❌ 防不住 | 只能缩短暴露时间：自动上锁、密码只在需要时解密。界面要如实说明 |
| 有人改写了 Life Atlas 程序本身 | ❌ 基本防不住 | WP-11 用 Electron Fuses 和 ASAR 完整性校验提高门槛 |
| 主密码和恢复密钥都丢了 | ❌ 无法找回（设计如此） | 没有后门。只能“重置密钥库”重新开始（旧密钥库文件保留，将来找到恢复密钥还能用）。创建时强制确认恢复密钥已保存 |

## 3. 密码学规格

| 项目 | 规定 |
| --- | --- |
| 口令派生 | Argon2id v1.3（0x13），`memoryKiB = 131072`（128 MiB），`iterations = 3`，`parallelism = 1`，输出 32 字节，盐 16 字节随机 |
| 口令派生实现 | `hash-wasm` 的 `argon2id()`，在主进程的 `worker_threads` 线程里执行（约 1 秒，**不得在主线程跑**，否则所有窗口卡死） |
| 对称加密 | AES-256-GCM（Node `crypto`），nonce 12 字节随机，认证标签 16 字节；每次加密都用新的 nonce |
| 恢复密钥派生 | HKDF-SHA256：`ikm = 恢复密钥的 32 字节`，`salt = 16 字节随机`，`info = "life-atlas/vault/v1/recovery-kek"`，输出 32 字节 |
| 随机数 | 只用 `crypto.randomBytes` / `crypto.randomInt`；禁止 `Math.random` |
| 口令规范化 | `password.normalize("NFKC")`，不去空格 |
| 二进制编码 | JSON 里用标准 Base64（带 `=` 填充）；SQLite 里密文用 BLOB |
| 密文布局 | `nonce(12) ‖ ciphertext ‖ tag(16)` |

### 3.1 必须通过的已知答案测试（总设计师已在本机用 Node 24.17 原生 Argon2 和 HMAC 实算确认）

**Argon2id**：`password = "password"`，`salt = "somesalt"`（ASCII），`m = 65536 KiB`，`t = 2`，`p = 1`，输出 32 字节：

```
09316115d5cf24ed5a15a31a3ba326e5cf32edc24702987c02b6566f61913cf7
```

（等价于 PHC 编码 `$argon2id$v=19$m=65536,t=2,p=1$c29tZXNhbHQ$CTFhFdXPJO1aFaMaO6Mm5c8y7cJHAph8ArZWb2GRPPc`。同参数但 `p = 4` 时输出 `1a9677b0afe81fda7b548895e7a1bfeb8668ffc19a530e37e088a668fab1c02a`。）

另外：在普通 Node 下（`crypto.argon2Sync` 可用时），对 3 组随机输入比较 `hash-wasm` 与 `crypto.argon2Sync("argon2id", …)` 的结果必须完全一致；不可用时跳过此交叉测试并在输出里注明。

总设计师 2026-11-01 实测 `hash-wasm@4.12.0`：在 `worker_threads` 里跑上面的已知答案测试结果一致；正式参数（128 MiB、t=3、p=1）在普通 Node 里约 365 ms、在 Electron 44 的 Node 里约 414 ms，主线程事件循环最大延迟约 11 ms。

**HKDF**（恢复密钥派生，`info = "life-atlas/vault/v1/recovery-kek"`，输出 32 字节）：

- `ikm` = 32 个 `0x00`，`salt` = 16 个 `0x00` → `c46567b0ad7d87efd6c722eb29a94293f72ca1bdecbbde1ca3558953d8019fab`
- `ikm` = `0x00…0x1f`，`salt` = `0xff, 0xfe, …, 0xf0`（16 字节，从 0xff 递减）→ `03d284dbe6a0c1c64560db1aac622dd3bdbd3bd51dee778f58762d4219718810`

**AES-256-GCM 密文布局**：key = 32 个 `0x11`，nonce = 12 个 `0x22`，AAD = `LA-VAULT-1|item|vault-test|vi_test`（UTF-8），明文 `hello vault`（UTF-8）→ `nonce ‖ ciphertext ‖ tag` 的十六进制为 `2222222222222222222222227f926b25afefe93e9053aa14ce8361ff7983e0535b79ae5f4a3690`。

| T（Unix 秒） | SHA1（密钥 `"12345678901234567890"`） | SHA256（密钥 `"12345678901234567890123456789012"`） | SHA512（密钥为 `"1234567890"` 重复到 64 字节） |

| 59 | 94287082 | 46119246 | 90693936 |
| 1111111109 | 07081804 | 68084774 | 25091201 |
| 1111111111 | 14050471 | 67062674 | 99943326 |

## 4. 密钥层级与流程

```
主密码 ──Argon2id(salt_pw)──▶ KEK_pw ──AES-GCM 包裹──▶ wrap_password ┐
                                                                        ├─▶ DEK（32 字节随机，真正加密条目的密钥）
恢复密钥 ──HKDF(salt_rk)────▶ KEK_rk ──AES-GCM 包裹──▶ wrap_recovery ┘
DEK ──AES-GCM──▶ 每个条目的密文
```

**总规则：每次“设置主密码”或“生成恢复密钥”，都会同时生成新的 DEK、新的恢复密钥，并用新 DEK 重新加密全部条目。** 原因：旧快照和旧备份里保存着旧的包裹；如果 DEK 不变，拿到旧密码（或旧恢复密钥）再加上一份旧快照，就能解开当前的全部条目。

- **创建**：生成 `vaultId`（UUID v4）、DEK、恢复密钥（32 字节）、两个盐；派生两个 KEK；分别包裹 DEK；写入头部；`vault_state.recoveryConfirmed = "false"`。**恢复密钥本身不写入磁盘**，只保存在主进程内存（“待确认的恢复密钥”）里，返回给界面显示。
- **确认恢复密钥**：用户输入最后两组，与内存里的待确认恢复密钥比较；正确 → `recoveryConfirmed = "true"`，内存里的恢复密钥 `fill(0)` 并丢弃。待确认期间，复制（`copyPendingRecoveryKey`）和保存恢复卡（`saveRecoveryKit`）都使用内存里的这一份，界面不需要把恢复密钥传回主进程。
- **恢复密钥未确认**：`recoveryConfirmed = "false"` 时，条目接口（`list`、`getItem` 等）返回 `E_LOCKED`（`message: "recovery-unconfirmed"`）。如果用户在确认前关闭了窗口或应用（内存里的恢复密钥随之消失，无法再显示），下次解锁成功后 `unlock` 返回 `requiresRecoveryKeyRegeneration: true`，界面必须先走“重新生成恢复密钥”并确认，才能看到条目。
- **解锁**：用主密码派生 KEK_pw → 解包 DEK；GCM 认证失败即“密码错误”。
- **上锁**：`DEK.fill(0)` 后置空；内存里的待确认恢复密钥 `fill(0)` 并丢弃；清空主进程里的条目摘要缓存；清理计时器；若剪贴板仍是复制过的内容则清空；通知密钥库窗口回到锁屏并清空界面状态。所有临时 KEK 用完立即 `fill(0)`。
- **轮换（内部步骤，下面三个流程都调用它）**：生成新 DEK 与新恢复密钥 → 在**一个事务**里：用旧 DEK 解密每个条目、用新 DEK 重新加密（新 nonce，AAD 不变）、用新 KEK 重新生成 `wraps.password` 与 `wraps.recovery`（新盐）、写入新头部、`recoveryConfirmed = "false"` → 提交后旧 DEK `fill(0)`。任何一步失败：事务回滚，密钥库保持原样，返回 `E_IO`。`vaultId` 不变。
- **修改主密码**：先用当前密码解包验证 → 新密码通过强度规则（4.1）→ 轮换 → 返回新恢复密钥，界面要求确认。旧主密码和旧恢复密钥对当前密钥库全部失效。
- **用恢复密钥找回**：校验恢复密钥格式与校验位 → HKDF 派生 KEK_rk → 解包 DEK → **强制设置新主密码** → 轮换 → 返回新恢复密钥，界面要求确认后才进入。
- **重新生成恢复密钥**：已解锁 + 再次输入主密码 → 轮换 → 返回新恢复密钥并要求确认。旧恢复密钥对当前密钥库立即失效。
- **重置密钥库**（两样都忘了）：在**锁屏**（以及设置页）提供入口“忘记了主密码和恢复密钥？重置密钥库”。用户输入确认短语“重置我的密钥库”并等待 10 秒倒计时 → `resetVault({ confirmPhrase })` → 主进程关闭 vault.db 连接、做 WAL 检查点（04 第 7.1 节第 9 步同样的方法）→ 把 `vault.db` 移到 `snapshots\<时间>-vault-reset\vault.db`（**不删除**，以后找到恢复密钥还能用）→ `status().exists` 变为 `false` → 进入首次创建流程。重置不需要主密码。
- **主密码只在密钥库窗口输入**：任何需要主密码的操作（解锁、改密码、导出含密钥库的备份、开启含密钥库的定期备份、开启了“显示前验证”时的显示）都只在密钥库窗口里输入。工作区窗口发起这类操作时，主进程打开/聚焦密钥库窗口并显示确认请求（第 10 节），工作区窗口只会收到“已确认 / 已取消 / 已过期”。界面“安全说明”要告诉用户：**在任何其他地方看到索要主密码的输入框，都不是 Life Atlas 的正常行为**。
- **所有主密码校验共用一个失败计数**（第 4.3 节），包括确认请求里的校验。

### 4.1 主密码规则（创建与修改时检查，纯函数，可单测）

1. 至少 12 个字符（按 Unicode 码点计数）。
2. 至少 5 个不同字符。
3. 不是常见密码，也不是“常见密码 + 数字或符号”。判断方法（不区分大小写）：设 `p` 为密码的小写形式；去掉 `p` 开头和结尾的所有非字母字符（字母指 Unicode 字母）得到 `core`；`p` 在表里，或者 `core` 至少 4 个码点、在表里、并且 `core` 的码点数 × 2 ≥ `p` 的码点数，就判为常见密码。已知答案：`Password1234`、`!!sunshine2026`、`iloveyou!!!!` 判为常见；`Dragon!!12345`、`Superman123456789`、`monkey-business-42`、`correct horse battery` 不算。（表里没有长度 ≥ 10 的条目，所以只比较整条是不够的。）表取自 SecLists `Passwords/Common-Credentials/10k-most-common.txt` 前 1000 条（MIT）。总设计师已把它连同来源说明放在 `docs/blueprint/data/commonPasswords.txt`（7604 字节，SHA-256 `60f8bc6795ce51e2dd95247bfbb0cfd86dab5760471e13087dffa4560cc78706`），WP-06 原样复制为 `electron/main/vault/commonPasswords.txt`；读取时跳过以 `#` 开头的行。
4. 不能是简单序列或重复：整个密码（转小写后）是 `0123456789`、`abcdefghijklmnopqrstuvwxyz`、`qwertyuiopasdfghjklzxcvbnm` 中任意一个的连续片段（正序或倒序），或者是同一段字符重复两次以上（如 `abcabcabcabc`）。

界面显示强度条（弱/中/强），按 `码点长度 × log2(字符集大小)` 估算，结果保留一位小数。字符集大小：出现小写字母 +26、大写字母 +26、数字 +10、其他可打印 ASCII 符号（含空格）+33、任何非 ASCII 字符 +100。< 60 弱，60–80 中，> 80 强。规则 1–4 不满足时不允许提交；“弱”只提示不阻止。已知答案：`abcdefghijkx` → 56.4（弱），`我的主密码很长很长很长` → 73.1（中），`Correct-Horse-9` → 98.5（强），`Tr0ub4dor&3xyz!!` → 105.1（强）。

### 4.2 恢复密钥格式

- 载荷：32 字节随机数 + 2 字节校验（`SHA-256(32 字节)` 的前 2 字节）= 34 字节。
- 编码：把 34 字节按大端顺序排成 272 个比特，末尾补 3 个 0 比特凑成 275 比特，每 5 比特一个字符，用 Crockford Base32 字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ` 映射，得到 55 个字符；显示为 `LA1-` 加 11 组、每组 5 个字符，用 `-` 分隔。
- 解析：转大写，去掉空格和 `-`，去掉开头的 `LA1`，把 `O` 换成 `0`、`I` 和 `L` 换成 `1`；必须正好 55 个字符且都在字母表里；解码后末尾 3 个补位比特必须为 0；再校验 2 字节校验位。任何一步失败都直接提示“恢复密钥有误”，**不进行解密尝试**。
- “最后两组”指第 10、11 组（各 5 个字符），确认时同样先规范化再比较。
- **已知答案**（总设计师实算）：
  - 32 个 `0x00` 字节 → `LA1-00000-00000-00000-00000-00000-00000-00000-00000-00000-00000-06CT0`
  - 字节 `0x00, 0x01, …, 0x1f` → `LA1-000G4-0R40M-30E20-9185G-R38E1-W8124-GK2GA-HC5RR-34D1P-70X3R-FP638`

### 4.3 失败节流

- `vault_state` 保存 `failedAttempts` 与 `lockoutUntil`（不是秘密，重启后仍有效）。
- 每次密码错误 `failedAttempts + 1`；达到 5 次起，`lockoutUntil = 现在 + min(30 秒 × 2^(failedAttempts − 5), 15 分钟)`。
- 等待期内调用解锁（以及确认请求）直接返回 `E_THROTTLED` 和 `retryAfterMs`，**不运行** Argon2id。
- 成功解锁后清零。时钟必须可注入，单测用假时钟。

## 5. 存储格式（vault.db）

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA secure_delete = ON;      -- 删除的数据页用 0 覆盖

CREATE TABLE IF NOT EXISTS vault_header (id INTEGER PRIMARY KEY CHECK (id = 1), json TEXT NOT NULL);
CREATE TABLE IF NOT EXISTS vault_items  (id TEXT PRIMARY KEY, blob BLOB NOT NULL) WITHOUT ROWID;
CREATE TABLE IF NOT EXISTS vault_state  (key TEXT PRIMARY KEY, value TEXT NOT NULL);  -- 节流计数、设置（非秘密）
```

`vault_state` 的键：`failedAttempts`（数字字符串）、`lockoutUntil`（ISO 时间或空字符串）、`recoveryConfirmed`（`"true"`/`"false"`）、`settings`（JSON，形状见 11 第 4.8 节）。

`vault_header` 表 `json` 列的内容（字段名固定）：

```json
{
  "kind": "life-atlas-vault",
  "formatVersion": 1,
  "vaultId": "8b1e…",
  "createdAt": "2026-11-01T02:00:00.000Z",
  "kdf": { "alg": "argon2id", "version": 19, "memoryKiB": 131072, "iterations": 3, "parallelism": 1, "saltB64": "…" },
  "wraps": {
    "password": { "alg": "A256GCM", "blobB64": "…" },
    "recovery": { "alg": "A256GCM", "kdf": "hkdf-sha256", "saltB64": "…", "blobB64": "…" }
  },
  "padding": 512
}
```

### 5.1 附加数据（AAD）字符串——逐字节一致

AAD 是 UTF-8 字符串，字段之间用竖线分隔，尖括号部分替换为实际值（数字用十进制，无空格）：

```text
主密码包裹：   LA-VAULT-1|wrap|password|<vaultId>|argon2id|<memoryKiB>|<iterations>|<parallelism>
恢复密钥包裹： LA-VAULT-1|wrap|recovery|<vaultId>
条目：         LA-VAULT-1|item|<vaultId>|<itemId>
```

例：`LA-VAULT-1|wrap|password|8b1e…|argon2id|131072|3|1`。

### 5.2 条目明文的封装

`明文 = 4 字节大端长度 ‖ 条目 JSON 的 UTF-8 ‖ 0x00 填充到 512 的整数倍`（4 字节长度也计入总长度）。解密后按长度取出 JSON。填充是为了不让密文长度暴露内容长度。

`vault_items.id` 用随机 ID（`vi_` + 16 字节随机数的十六进制），不含任何可读信息。

```json
  ],
  "subtitleFieldId": "f_user",
  "history": [ { "fieldId": "f_pass", "value": "旧值", "changedAt": "…" } ],
  "expiresAt": null,
  "deletedAt": null,
  "createdAt": "…",
  "updatedAt": "…"
}
```

- `kind` 取值：`text`、`secret`、`url`、`email`、`number`、`date`、`multiline`、`totp`。`secret` 和 `totp` 永远是敏感字段；其他类型默认不敏感，用户可以手动标记为敏感。
- 字段 ID：主进程生成，`f_` + 8 位随机十六进制。
- `history`：敏感字段被修改或删除时把旧值放进去，每个字段最多保留 10 条（WP-11 才在界面上展示，WP-06 就要写入）。
- `deletedAt` 不为空表示在密钥库回收站里；超过 30 天的在下次解锁时永久删除。

### 6.1 内置条目类型（新建时的预设字段，用户可增删字段）

| type | 界面名称 | 预设字段（`*` 表示敏感） |
| --- | --- | --- |
| `login` | 登录账号 | 网址、用户名、密码*、两步验证*、备注 |
| `apiKey` | API 密钥 | 服务商、环境（生产/测试/开发）、Key 名称、API Key*、Secret*、权限范围、到期日、控制台网址、备注 |
| `server` | 服务器 / SSH | 主机、端口、用户名、密码*、私钥*（多行）、主机指纹、备注 |
| `database` | 数据库连接 | 类型、主机、端口、数据库名、用户名、密码*、连接串*、备注 |
| `secureNote` | 安全笔记 | 内容*（多行） |
| `recoveryCodes` | 恢复码 | 服务、恢复码*（多行，每行一个）、备注 |
| `custom` | 自定义 | 无，全部自己加 |

`apiKey` 的“到期日”写入 `expiresAt`，用于到期提醒（WP-11）。

## 7. 运行时行为

| 行为 | 规定 |
| --- | --- |
| 解锁后的内存 | 主进程只缓存**条目摘要**（11 第 4.7 节）。需要详情、显示、复制时再从数据库解密该条目，用完丢弃明文 |
| 发给界面的详情 | 不敏感字段带值；敏感字段只给 `{ id, label, kind, sensitive: true, masked: true, hasValue }` |
| 显示敏感字段 | 用户点“显示”才调用 `revealField`；界面 20 秒后或窗口失焦时自动重新遮盖 |
| 复制 | `copyField`（以及 `copyPendingRecoveryKey`）在**主进程**写剪贴板，内容不经过界面；记录值的 SHA-256；N 秒后（默认 30，可选 10/30/60/90）若剪贴板文本的 SHA-256 仍相同则清空；上锁和退出时同样检查 |
| 自动上锁 | 默认闲置 5 分钟（可选 1/5/15/30/60）。闲置判断：密钥库窗口 `activity()` 心跳（最多每 15 秒一次）与 `powerMonitor.getSystemIdleTime()` 取较严者。系统锁屏 `lock-screen`、睡眠 `suspend`、关闭密钥库窗口、退出应用都立即上锁。可选“窗口最小化时上锁”（默认关） |
| 上锁倒计时 | 剩余不到 60 秒时在顶栏提示“将在 N 秒后上锁” |
| 敏感操作再次验证 | 修改主密码、重新生成恢复密钥、导出包含密钥库的备份、开启含密钥库的定期备份，都要在密钥库窗口里再次输入主密码（即使已解锁）。确认请求只校验密码，**不改变**上锁/解锁状态。重置密钥库不用主密码，用确认短语（第 4 节）。可选“显示/复制密码前也验证”（默认关） |
| 截图保护 | 密钥库窗口创建后立即 `setContentProtection(true)` |
| TOTP | 主进程计算；`getTotp` 返回 `{ code, periodSeconds, validForSeconds }`，界面倒计时结束再取下一个。支持 `otpauth://totp/…` 链接和裸 Base32 密钥；算法 SHA1/SHA256/SHA512，位数 6/8，步长 30/60；缺省 SHA1、6 位、30 秒 |
| 密码生成器 | 随机模式：长度 8–128（默认 20），大写/小写/数字/符号可选，可排除易混字符 `Il1O0`，保证每个选中的字符类至少出现一次；用 `crypto.randomInt`。口令短语模式在 WP-11 |
| 恢复卡 | `saveRecoveryKit` 写出一个独立 HTML（不引用任何外部资源），内容：标题、恢复密钥（大号等宽字体分组）、创建日期、vaultId 前 8 位、使用说明。目标路径在数据目录内，或路径命中 02 第 3 节的同步盘规则时，拒绝保存并提示“恢复卡不要放在这台电脑的数据目录或同步盘里，建议打印或存到 U 盘” |
| 外部网址 | 详情里网址旁的“打开”按钮走主进程确认框后用系统浏览器打开 |
| 界面存储 | 密钥库窗口的代码**禁止**使用 localStorage、sessionStorage、IndexedDB、Cookie、Cache API |
| 测试钩子 | 缩短自动上锁、剪贴板、确认请求过期时间的环境变量（11 第 5 节）只在测试钩子开启时读取；release 构建里不存在任何改变时间或 KDF 参数的途径 |

## 8. 必须自动化的安全测试（WP-06/07/08 的 AC 会逐条引用）

| 编号 | 测试 | 通过标准 |
| --- | --- | --- |
| S1 明文扫描 | 每个字段都放唯一标记（如 `LA-MARKER-<随机hex>`），上锁并退出后，递归扫描整个数据目录（含 `-wal`、日志、快照、`runtime\` 缓存）以及导出的备份包（原始字节和解压后的每个条目），搜索标记的 UTF-8 与 UTF-16LE 形式 | 命中数 = 0 |
| S2 篡改 | 改密文中任意 1 字节 | 该条目提示“条目已损坏，无法解密”，其他条目正常，应用不崩溃 |
| S3 互换 | 交换两个条目的 blob | 两个都解密失败 |
| S4 头部篡改 | 修改 `kdf.memoryKiB` 或 `wraps` 中任意字节 | 解锁失败，提示“密码错误或密钥库文件已被修改” |
| S5 隔离 | 工作区窗口里 `window.lifeAtlasVault === undefined`；主进程处理函数收到非密钥库窗口的调用 | 返回 `E_FORBIDDEN` |
| S6 自动上锁 | 单元测试用假时钟；端到端测试用 `LIFE_ATLAS_TEST_AUTOLOCK_MS=2000`（测试钩子开启时才生效） | 闲置后界面回到锁屏，DOM 中没有任何条目标题；`list()` 返回 `E_LOCKED` |
| S7 剪贴板 | 单元测试用假剪贴板；端到端测试用 `LIFE_ATLAS_TEST_CLIPBOARD_MS=1500` | 到时清空；期间若用户复制了别的内容，则**不**清空 |
| S8 节流 | 假时钟下连续 5 次错误 | 第 6 次立即返回 `E_THROTTLED`，`retryAfterMs ≈ 30000`，且没有调用 KDF |
| S9 恢复密钥 | 校验位错误 / 格式正确但不是本库的 / 正确 | 分别为：立即拒绝且不调用 HKDF 解包 / 解包失败 / 成功、强制设新密码、返回新恢复密钥 |
| S10 改密码 | 改密码并确认新恢复密钥后 | 旧密码失败，新密码成功，旧恢复密钥失败，新恢复密钥成功，条目逐字段一致 |
| S11 KDF | 第 3.1 节已知答案 + 交叉验证 | 全部一致 |
| S12 TOTP | 第 3.1 节 18 个值 | 全部一致 |
| S13 截图保护 | 密钥库窗口 | `isContentProtected()` 为 true（若该 API 不存在，用替身断言调用过 `setContentProtection(true)`） |
| S14 不联网 | 密钥库全流程端到端测试 | 网络请求数 = 0 |
| S15 界面存储 | 源码检查 `src/vault-ui/` | 不出现 `localStorage`、`sessionStorage`、`indexedDB`、`document.cookie`、`caches.` |
| S16 轮换 | 保存一份改密码前的 `vault.db` 副本，然后改密码 | 用旧密码 + 旧副本的头部解出的 DEK，无法解密当前 `vault.db` 中任何条目；注入失败（`vault-rotate`）时密钥库与轮换前逐字节相同，旧密码仍可解锁 |

`tools/scan-plaintext.mjs` 用法：`node tools/scan-plaintext.mjs <目录或文件…> --markers <标记文件>`（标记文件每行一个标记），输出每个命中（文件、偏移、编码），无命中时退出码 0，有命中退出码 1。zip 文件要逐条解压后扫描。

**KDF 参数**：单元测试里为了速度，可以通过**参数注入**（`createVaultService({ kdfParams })`）把 `memoryKiB` 降到 8192；已知答案测试与至少一个完整流程单元测试必须用正式参数 131072。端到端测试一律用正式参数。没有任何环境变量可以改变 KDF 参数。

## 10. 密钥库窗口接口

完整函数表与数据形状见 `11-接口契约.md` 第 2 节与第 4.7–4.9 节。本节只写确认请求的规则：

- 主进程收到工作区窗口的敏感操作（导出含密钥库的备份、开启含密钥库的定期备份），或密钥库窗口里开启了“显示前验证”的显示操作 → 生成 `requestId`（一次性，默认 2 分钟过期）→ 打开/聚焦密钥库窗口并推送 `onConfirmRequest` → 密钥库窗口显示一个独立的确认框（说明是什么操作、来自哪里，例如“导出完整备份（包含密钥库）”）→ 用户输入主密码 → `confirmRequest`。
- 确认请求在密钥库已锁和已解锁两种状态下都可以完成；只校验密码，不改变上锁状态；密码错误计入共用失败计数，节流期内返回 `E_THROTTLED`。
- 结果只以“已确认 / 已取消 / 已过期”返回给发起方；同一个 `requestId` 不能用第二次。
- 主进程内部接口：`requestConfirmation({ kind, title, description }) → Promise<"confirmed" | "cancelled" | "expired">`。

工作区窗口只能看到 `app.openVaultWindow()`、`app.getVaultStatus()`（`{ exists, locked }`）和 `app.onVaultStatusChanged()`。

## 11. 界面流程

视觉已定为墨白（`12-视觉规范-墨白.md` 第 7、8 节；WP-07 第 2 节写了密钥库窗口的具体做法）。以下是交互骨架，所有文案用中文。

1. **首次进入**：说明页（三句话：这里加密保存账号与密钥；主密码无法找回；接下来会生成恢复密钥）→ 设置主密码（两次输入、强度条、规则逐条打勾）→ 显示恢复密钥（大号等宽字体分组显示，“保存恢复卡”“复制”两个按钮，提示“请离线保存，不要存在这台电脑上”）→ 输入恢复密钥最后两组确认 → 进入空密钥库。
2. **锁屏**：锁孔圆盘（12 第 8 节）、标题“密钥库已上锁”、主密码输入框（自动聚焦，回车解锁）、错误提示与等待倒计时、链接“忘记主密码？使用恢复密钥”、次要链接“忘记了主密码和恢复密钥？重置密钥库”。
3. **用恢复密钥找回**：输入恢复密钥 → 设置新主密码（同首次规则）→ 显示新的恢复密钥 → 确认最后两组 → 进入。
4. **重置密钥库**：说明“当前密钥库会被移到快照文件夹保留，不会删除；重置后需要重新创建”→ 输入确认短语“重置我的密钥库”→ 10 秒倒计时后按钮可点 → 重置 → 回到首次进入流程。
5. **主界面**（三栏，这是密钥库窗口的例外，不受“不要右侧详情栏”规则约束）：
   - 顶部工具栏：搜索框（只搜摘要）、“闲置 N 分钟后上锁”、“上锁”按钮。
   - 左栏：全部、收藏、各类型、标签；底部“回收站”“设置”。
   - 中栏：当前分类名与条目数、“新建”、排序（最近修改/名称）、条目行（标题首字的方块、标题、副标题、类型名、到期标记）。
   - 右栏：详情，字段逐行显示；敏感字段显示为 `••••••••` + “显示”“复制”；TOTP 显示 6/8 位码和圆形倒计时；网址有“打开”。右上“编辑”。
6. **编辑**：表单；敏感字段默认不回填明文，点“显示”才回填，或直接输入新值替换（提交时按 11 第 4.7 节的 `keepValue` 规则）；字段可增删、上下移动、切换敏感；内嵌密码生成器。
7. **设置**：自动上锁时间、剪贴板清除时间、最小化时上锁、显示密码前验证、修改主密码（完成后显示新恢复密钥并确认）、重新生成恢复密钥、安全说明（第 2 节通俗版）、重置密钥库。
8. 快捷键：`Ctrl+L` 立即上锁，`Ctrl+F` 聚焦搜索，`Ctrl+N` 新建条目。

## 12. 与备份的关系

见 `04-备份与恢复规格.md` 第 5 节。要点：备份包里的密钥库是 `vault.db` 内容的 JSON 形式（头部 + 全部条目密文），**从不解密**；导入后密钥库处于上锁状态，用导出时的主密码或恢复密钥解锁。导出包含密钥库时，要在密钥库窗口里通过确认请求再次输入主密码，以确认用户记得这把钥匙。
