# 04 备份与恢复规格

用户的原话：“导出了这些文件在导入的时候能还原我们原来的数据，并且在导出过程中密钥的部分也是加密的，导入回来的时候也能还原。”

本文件定义三样东西：**备份包**（可以拿到别处保存、导入还原的单个文件）、**快照**（应用在数据目录里自动保留的副本）、**恢复流程**（把备份包或快照还原成当前数据）。格式字段名都是规定，不得改名。

## 1. 三种保护各管什么

| 机制 | 存在哪里 | 谁触发 | 防什么 |
| --- | --- | --- | --- |
| 快照 | `<DataRoot>\snapshots\` | 自动：每天、升级前、迁移前、恢复前、重置密钥库前；也可以手动 | 误操作、升级出错、数据库损坏 |
| 完整备份（`.lifeatlas`） | 用户选的位置（另一块硬盘、U 盘、同步盘） | 手动导出；可设置每周自动导出到指定文件夹 | 硬盘损坏、电脑丢失、重装系统、换电脑 |
| 页面导出（Markdown/HTML/PDF/JSON） | 用户选的位置 | 手动 | 把单个页面分享出去或长期可读（已有功能，不变） |

## 2. 备份包格式 v1

扩展名 `.lifeatlas`。本质是一个 ZIP 文件（不加密的情况下）。

```
manifest.json                          ← 必须是 zip 里的第一个条目
workspace/meta.json                    ← { schemaVersion, workspaceId, savedAt, ui, extras }（extras：工作区对象里白名单集合与上述字段以外的其他顶层字段，原样保存，没有就是 {}）
workspace/entities/<collection>.jsonl  ← 每行一个实体，按 id 升序；空集合也要有空文件
assets/index.json                      ← [{ sha256, size, mime, originalName, createdAt }]
assets/<sha256>                        ← 附件原始字节
vault/vault.json                       ← 可选；见第 5 节；内容全部是密文
```

- `<collection>` 取 02 第 4.2 节的白名单。
- JSONL：每行 `JSON.stringify(实体)`（无缩进），按 `id` 的字符串顺序升序，行尾 `\n`，UTF-8 无 BOM；空集合是 0 字节文件。`manifest.json`、`workspace/meta.json`、`assets/index.json` 用 `JSON.stringify(值, null, 2)`。
- zip 里只放文件条目，**不放目录条目**（JSZip 写入时用 `createFolders: false`）；读取时遇到以 `/` 结尾的目录条目直接忽略，不算多余文件。
- `assets/index.json` 每个附件一项；两个附件内容相同时，`assets/<sha256>` 文件只放一份，但 `index.json` 里仍是两项（浏览器迁移包里它们的 `legacyAttachmentId` 不同）。`manifest.assets.count` 与 `totalBytes` 按**不重复的文件**计算。
- 压缩方式：MIME 为 `image/jpeg`、`image/png`、`image/webp`、`image/gif`、`video/*`、`audio/*`、`application/pdf`、`application/zip` 的附件用 STORE（不压缩），其余条目（包括所有 JSON/JSONL）用 DEFLATE。

### 2.1 manifest.json

```json
{
  "kind": "life-atlas-backup",
  "formatVersion": 1,
  "createdAt": "2026-11-01T02:00:00.000Z",
  "app": { "name": "Life Atlas", "version": "0.1.0", "platform": "desktop" },
  "workspace": {
    "schemaVersion": 12,
    "workspaceId": "ws-…",
    "counts": { "folders": 13, "pages": 120, "dataSources": 4, "databaseItems": 380, "attachments": 52 }
  },
  "assets": { "count": 52, "totalBytes": 734003200 },
  "vault": { "included": true, "vaultId": "8b1e…", "formatVersion": 1, "itemCount": 37 },
  "files": [
    { "path": "workspace/meta.json", "size": 812, "sha256": "…" },
    { "path": "workspace/entities/pages.jsonl", "size": 532118, "sha256": "…" },
    { "path": "assets/9f86d0…", "size": 120442, "sha256": "9f86d0…" }
  ]
}
```

- `app.version` 取 `package.json` 的 `version`；`app.platform` 取 `"desktop"` 或 `"browser"`（浏览器迁移包）。
- `vault.included` 为 `false` 时没有 `vault/` 目录，`vaultId`、`formatVersion`、`itemCount` 省略。
- `files` 列出除 `manifest.json` 以外的**每一个**文件，按 `path` 升序。附件文件的 `sha256` 必须等于文件名。
- 不允许出现 `files` 之外的文件；读取时发现多余文件，记录警告 `EXTRA_FILE` 并忽略。
- 路径只能是正斜杠相对路径，只含 `A–Z a–z 0–9 . _ - /`，不能含 `..`、盘符、反斜杠或以 `/` 开头（防止解压穿越）。
- 写 zip 时 manifest 要第一个写入，但它包含后面文件的哈希：先把工作区 JSONL 与 meta 在内存/临时文件里生成并计算哈希（附件的哈希就是文件名，不用重算），再写 manifest，再依次写其他文件。

### 2.2 浏览器迁移包（WP-02 产出）

浏览器模式导出的包与桌面版格式相同，区别只有：

- `app.platform = "browser"`；`vault.included = false`（浏览器模式没有密钥库）。
- IndexedDB 里的附件（`life-atlas.attachments.v1`）读出来写进 `assets/`。
- 工作区 JSON 里的 `data:*;base64,…` 字符串（页面图标、封面等）**原样保留**在实体里，不在浏览器里转换；桌面版导入时再转成附件文件（第 7.3 节）。
- 引用 IndexedDB 附件的地方保持原值（`blob:…#life-attachment=<id>` 和附件实体的 `storageKey`），并在 `assets/index.json` 的每一项里额外写 `"legacyAttachmentId": "<id>"`，供桌面导入时改写引用。
- `workspaceId`：浏览器适配器在加载时补齐（02 第 4.3 节），所以迁移包里一定有。

## 3. 完整性规则

读取任何备份包（导入、校验、恢复）都必须按顺序做完这些检查，**任何一步失败都不能修改当前数据**。每条检查失败时的问题代码见 11 第 4.4 节。

1. 是合法 zip（或合法的加密容器，第 4 节）。
2. 第一个条目是 `manifest.json`，`kind === "life-atlas-backup"`。
3. `formatVersion` 不大于当前支持的版本；否则提示“这个备份来自更新版本的 Life Atlas，请先升级应用”。
4. `workspace.schemaVersion` 不大于当前 `CURRENT_SCHEMA_VERSION`；否则同上。
5. `files` 里每个路径合法、每个文件都存在、大小与 SHA-256 全部吻合（流式计算，不把大文件读进内存）。
6. 每个 `.jsonl` 每行都能解析成对象且有字符串 `id`；`counts` 与实际行数一致。
6a. `workspace/entities/` 下必须有 `requiredCollections(workspace.schemaVersion)` 里每个集合的文件（`src/backup/format.js`，WP-16 加入）：后来才加入的集合只对足够新的备份是必需的（`pageVersions` 从 schema 16 起）。旧备份缺少这类文件时，该集合按空数组处理，不算 `MISSING_FILE`。
7. 若含 `vault/vault.json`：结构合法、`vaultId` 与 manifest 一致、每个条目 blob 是合法 Base64 且解码后长度至少 28 字节。

“校验备份”功能就是只做以上检查并给出报告，不做任何还原。

## 4. 可选：整包加密（WP-08）

用户勾选“加密整个备份”并设置一个**备份密码**时，输出文件仍叫 `.lifeatlas`，但内容是下面的加密容器，里面包着第 2 节的 zip：

```
偏移 0   魔数 8 字节："LAENC1\0\0"
偏移 8   头部长度 4 字节（大端无符号）
偏移 12  头部 JSON（UTF-8）
之后     连续的加密块
```

头部 JSON：

```json
{
  "kind": "life-atlas-encrypted-backup",
  "formatVersion": 1,
  "kdf": { "alg": "argon2id", "version": 19, "memoryKiB": 131072, "iterations": 3, "parallelism": 1, "saltB64": "…" },
  "cipher": "A256GCM-STREAM",
  "chunkSize": 1048576,
  "noncePrefixB64": "…(7 字节)"
}
```

- 头部 JSON 的字节 = `JSON.stringify(头部对象)`，键的顺序**必须**与上面的示例完全相同（`kind, formatVersion, kdf{alg, version, memoryKiB, iterations, parallelism, saltB64}, cipher, chunkSize, noncePrefixB64`），没有空格和换行。
- 密钥：`Argon2id(备份密码 NFKC, salt)` 得到 32 字节。
- **不在目标位置留下明文**：导出时先把普通 zip 写到 `<DataRoot>\.staging-export-<时间>\package.zip`（与数据在同一块盘上），校验通过后再流式加密写到目标位置的临时文件，然后对临时文件做一次流式解密、比较解密结果的 SHA-256 与 `package.zip` 相同，最后改名并删除暂存目录。导入加密包时同样先解密到 `<DataRoot>\.staging-import-<时间>\package.zip` 再按第 3 节检查，结束后删除。
- **已知答案**（总设计师实算；直接给定派生密钥，不经过 Argon2id，仅用于测试容器格式）：密钥 = 32 个 `0x42`，`saltB64` = 16 个 `0x24` 的 Base64，`noncePrefix` = `01 02 03 04 05 06 07`，`chunkSize` = 16（只在测试里用这么小的块）：

  | 明文 | 容器长度 | 容器的 SHA-256 |
  | --- | --- | --- |
  | 空（0 字节） | 282 | `63ff8495143fc3fae6f1a7a0ea49dca004498c46bd653bceef5af3ab32645fd3` |
  | `life atlas`（UTF-8，10 字节） | 292 | `7e1d839180c99f974dba4d2b2c8ec055d82c49710335b62704b1b4cc3f94c418` |
  | 16 个 `0x61` | 314 | `1263fee660ec2f46da9eae7cc2567fe40ae7ec8e523ed96bc3bbf76eb52688d8` |
  | 20 个 `0x62` | 318 | `d218d218c7a61765491ab7b8c399e59e9e6e56cc1a23977aaeb67a6d46dca9b4` |

  （16 字节的明文正好是一整块，所以后面还有一个空的最后一块；空明文只有一个空的最后一块。）
- 把 zip 字节流按 `chunkSize` 切块；第 i 块（从 0 开始）的 nonce = `noncePrefix(7) ‖ i(4 字节大端) ‖ last(1 字节，最后一块为 0x01，其余 0x00)`。
- 每块 AAD = 整个“魔数 + 头部长度 + 头部 JSON”字节的 SHA-256（32 字节）。
- 每块输出 `ciphertext ‖ tag(16)`；最后一块可以短于 `chunkSize`，可以为空（zip 长度恰为整数倍时）。
- 解密时：标签错误、块序号对不上、缺少 `last=1` 的块、`last=1` 之后还有数据，都判定为“备份密码错误或文件已损坏”。
- 备份密码与主密码是两回事；界面要说清楚：“忘记备份密码，这个备份就打不开”。备份密码规则同主密码（03 第 4.1 节）。
- 密钥库部分在整包加密时**仍然**保持它自己的加密（双层），不得为此解密密钥库。

## 5. 密钥库在备份包里的形态

`vault/vault.json`：

```json
{
  "kind": "life-atlas-vault-export",
  "formatVersion": 1,
  "header": { …vault.db 中 vault_header 表 json 列的内容，解析成对象… },
  "items": [ { "id": "vi_…", "blobB64": "…" } ],
  "state": { "settings": { …非秘密的设置… } }
}
```

规则：

1. 导出时**直接复制密文**，不解密、不重新加密、不改 `vaultId`。节流计数（`failedAttempts`、`lockoutUntil`）和 `recoveryConfirmed` 不导出。
2. 导出包含密钥库之前，主进程通过密钥库窗口的确认请求（03 第 10 节）让用户输入主密码，并用它实际解包一次 DEK 以确认正确（用完立即 `fill(0)`）。这样能保证导出的备份将来能被这把密码打开。主密码**不经过**工作区窗口。界面文案：“备份中的密钥库仍由你现在的主密码加密。恢复时需要这个主密码或恢复密钥。”
3. 密钥库处于“恢复密钥待确认”状态时，不允许导出含密钥库的备份（提示先完成恢复密钥确认），因为这时的恢复密钥可能还没有被保存。
4. 导入恢复密钥库时，把 `header` 与 `items` 原样写进新的 `vault.db`，状态为上锁，节流计数清零，`recoveryConfirmed = "true"`。
5. 往返一致性：导出 → 恢复 → 用同一主密码解锁 → 每个条目解密后与导出前逐字段相等。

## 6. 快照

- **内容**：对 `workspace.db` 与 `vault.db`（存在时）分别执行 `VACUUM INTO '<快照目录>\workspace.db'`（或 `node:sqlite` 的 `backup()`），得到一致性副本；附件文件是内容寻址且不可变的，快照**不复制附件**。
- **目录名**：`<UTC 时间 YYYY-MM-DDTHH-mm-ss-SSSZ>-<原因>`，例 `2026-11-01T02-00-00-000Z-daily`。
- **原因**：

  | 原因 | 什么时候做 | 包含 |
  | --- | --- | --- |
  | `daily` | 启动 60 秒后检查一次，之后每小时检查一次：最新的 `daily` 早于 20 小时前就做一个 | 工作区 + 密钥库 |
  | `pre-upgrade` | 启动时 `meta.lastAppVersion` 存在且不等于当前版本（写任何东西之前） | 工作区 + 密钥库 |
  | `pre-migration` | 启动时数据库的 `schemaVersion` 低于当前版本（迁移之前） | 工作区 |
  | `pre-restore` | 从备份或快照恢复之前 | 将被替换的那些文件 |
  | `manual` | 用户点“立即创建快照” | 工作区 + 密钥库 |
  | `vault-reset` | 重置密钥库之前（03 第 4 节；这里不是复制而是把原 `vault.db` 移进来） | 只有密钥库 |

- 每个快照目录里写 `snapshot.json`：`{ createdAt, reason, appVersion, schemaVersion, counts, files: [{ name, size, sha256 }], integrity }`。`integrity` 只在 `daily` 快照里有值：对快照副本执行 `PRAGMA integrity_check` 的结果，`"ok"` 或 `"failed"`；`failed` 时写错误日志，并在“备份与恢复”对话框的快照列表里标出“完整性检查未通过”、在对话框顶部显示红色提示“数据库完整性检查未通过，请立即导出完整备份”。
- **保留策略**（纯函数 `selectSnapshotsToDelete(snapshots, now)`，按 UTC 计算日期、周、月；周从周一开始）：
  - `daily`：保留 ① 最新的 7 个；② 当前周和之前 3 周（共 4 个日历周），每周最新的 1 个；③ 当前月和之前 5 个月（共 6 个日历月），每月最新的 1 个。三者的并集保留，其余 `daily` 删除。
  - `pre-upgrade`、`pre-migration`、`pre-restore`、`manual`：**每种原因分别**保留最新的 10 个。
  - `vault-reset`：永不自动删除。
  - 同一时间的快照按目录名排序决定新旧。
- **从快照恢复**：走第 7 节同样的“暂存 → 校验 → 交换”流程，并且恢复前先给当前状态再做一个 `pre-restore` 快照。恢复对话框里有两个选项：“恢复工作区”（快照包含工作区时默认勾选）与“恢复密钥库”（默认**不**勾选，说明“会把密钥库退回到快照时的状态，包括当时的主密码”）。`vault-reset` 快照只能恢复密钥库。
- 限制要在界面上说明：快照和数据在同一块硬盘上，硬盘坏了快照也没了，所以仍然需要完整备份。

## 7. 恢复流程（桌面版）

### 7.1 步骤

1. 用户选择 `.lifeatlas` 文件。若是加密容器，先输入备份密码。
2. 执行第 3 节全部检查，失败就显示具体原因（哪个文件、哪项不符）并结束。
3. 显示摘要：备份时间、来源（桌面/浏览器）、应用版本、各类数量、附件总大小、是否含密钥库。选项：
   - 恢复工作区与附件（必选，不能只恢复一半）；
   - 恢复密钥库（包含时才出现，默认勾选）。若当前已有密钥库，提示“当前密钥库会被备份中的版本替换，当前版本会保存在快照里”。
4. 用户点“恢复”，再次确认：“当前数据将被替换。替换前会自动保存快照，可以随时撤回。”
5. 做 `pre-restore` 快照。
6. 在 `<DataRoot>\.staging-<时间戳>\` 里构建新的 `workspace.db`：用 `PRAGMA journal_mode = DELETE` 创建（不产生 `-wal`）→ 写入实体与 meta（新的 `generation`；`lastFullBackupAt`、`lastAppVersion` 沿用当前数据库的值）→ 若 `schemaVersion` 较旧则运行迁移 → 浏览器迁移包执行第 7.3 节转换 → `assets` 表写入备份里的全部附件行（以及 7.3 新生成的附件行）→ `PRAGMA integrity_check` 必须为 `ok` → 数量与 manifest 一致（迁移导致的合法变化除外，写入恢复日志）。
7. 附件文件直接复制进正式的 `assets\`（内容寻址，新增文件不会破坏现有数据），已存在的跳过。注意：附件**表**的行只写进暂存数据库，不写进正在使用的数据库。
8. 若恢复密钥库：在暂存目录构建新的 `vault.db`（同样用 DELETE 模式）。
9. **交换**：
   1. 让工作区窗口停止保存（主进程拒绝后续 `applyChanges`，返回 `E_CONFLICT`）；
   2. 对要替换的每个数据库：`PRAGMA wal_checkpoint(TRUNCATE)` → 关闭这个数据库的**所有**连接 → 确认对应的 `-wal`、`-shm` 文件不存在（存在就中止恢复，返回 `E_IO`，不做任何改名）；
   3. 把现有 `workspace.db`（及 `vault.db`）改名为 `*.replaced-<时间戳>` → 把暂存文件移入 → 重新打开（恢复 WAL 模式）并读一遍校验；
   4. 成功后删除 `*.replaced-*` 和暂存目录；任一步失败：关闭新文件、删除它、把旧文件改名回去、重新打开旧数据库，提示失败原因，数据保持恢复前的样子。
10. 工作区窗口重新加载；密钥库窗口若开着，回到锁屏。
11. 在 `logs\` 写一份恢复记录：时间、来源文件名、结果、数量（不写内容）。

### 7.2 首次启动导入

首次启动向导提供两个选项：“新建空白工作区”和“从备份恢复”。后者走同样的第 7.1 节流程（此时没有现有数据，跳过第 5 步快照和第 9 步里的旧文件处理，直接把暂存文件移入）。

### 7.3 浏览器迁移包的转换（桌面导入时在暂存数据库里执行）

1. 对 `assets/index.json` 里带 `legacyAttachmentId` 的项：把附件实体 `{ provider: "local-ref", storageKey: <id> }` 改成 `{ provider: "asset", storageKey: <sha256>, checksum: <sha256> }`；把区块 `props.url` 里以 `#life-attachment=<id>` 结尾的地址改成 `life-asset://<sha256>`。
2. 把下面这些**指定字段**里的 `data:<mime>;base64,<数据>` 解码 → 存为附件文件（写入正式 `assets\`，行写入暂存数据库）→ 原字符串替换为 `life-asset://<sha256>`：
   - `pages[].icon`、`pages[].cover.value`（`cover.kind === "upload"` 时）；
   - `pageTemplates[].icon`、`pageTemplates[].cover.value`；
   - `databaseTemplates[].pageAppearance.icon`、`databaseTemplates[].pageAppearance.cover.value`；

   其他任何地方出现的 `data:` 文字（比如正文、代码块里写的）**一律不动**。
3. 转换后对第 2 条列出的同一批字段再检查一遍：不应残留 `data:…;base64` 和 `#life-attachment=`；检查结果写进恢复日志。

## 9. 往返测试（各 WP 的 AC 会引用）

夹具见 `10-测试夹具规格.md`。

**B1 完整往返**：满配工作区夹具（含至少 5 个附件，其中至少一个 > 20 MB；页面图标与封面各一个）+ 含 10 个条目的密钥库 → 导出 → 换一个全新的临时数据目录 → 导入 → 比较：

- 每个集合按 id 逐个比较实体，深度相等（`savedAt`、`updatedAt` 等时间字段也必须相等，恢复不得改写时间）；`ui` 深度相等；
- 每个附件的 SHA-256 相等；
- 密钥库用同一主密码解锁，每个条目解密后逐字段相等；
- 工作区界面能打开每一个页面而不报错。

**B2 浏览器迁移**：浏览器模式里放入含 data URL 图标、IndexedDB 附件的工作区 → 导出迁移包 → 桌面版首次启动导入 → 页面内容、数据库一致；图片与附件能显示；第 7.3 节第 2 条列出的字段里不再有 `data:…;base64` 和 `#life-attachment=`。

**B3 旧版本**：用 schema 10 的夹具（`tests/fixtures/workspace-v10.json`）做成备份包 → 导入后自动迁移到当前版本，内容不丢。

**B4 损坏**：分别篡改 manifest、某个 jsonl 的 1 字节、某个附件的 1 字节、删掉一个文件、加一个 `../evil.txt` 路径、`formatVersion: 2`、`schemaVersion` 高于当前 → 全部被拒绝，并给出对应的问题代码，当前数据不变。

**B5 中途失败**：在交换步骤人为注入失败（测试钩子 `restore-swap`）→ 当前数据与恢复前完全一致。

**B6 加密包**：加密导出 → 错误密码被拒绝 → 正确密码恢复后与 B1 同样逐项一致；改动加密文件任意 1 字节 → 拒绝；截掉最后一块 → 拒绝；在末尾追加数据 → 拒绝。

**B7 明文**：对含密钥库的备份包（加密和不加密两种）运行 S1 明文扫描 → 0 命中。
